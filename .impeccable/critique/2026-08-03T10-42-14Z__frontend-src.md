## Design Specificity Verdict

**Partially authored for this product, but built on a recognizable 2024 dark-admin kit.** The product-specific layer is credible — "Trading Monitor / AI chart control", C++ signal-engine surface, Telegram delivery language, mono market numerics, LONG/SHORT chips, scan loop, countdown/progress, score bars, "vision-driven signal desk" login copy — these could only be made for a monitoring desk. But the underlying composition (sidebar + topbar, indigo accent, rounded cards, glass blur, pill statuses, stat tiles, toast notifications, "Settings / Save / Retry / Loading" patterns) is category-interchangeable. The interface says *admin dashboard with trading labels* more strongly than *decisive signal desk built around threshold truth, confidence, and intervention*. The missed opportunity: making signal qualification and operational risk visually dominant everywhere, not one more card among many.

**Deterministic scan**: 6 findings (all warnings, exit 0) — 3× `layout-transition` (AppSidebar 140/324, DashboardView 312), 3× `side-tab` (DashboardView 282, EngineView 255, StrategyView 129). This is a much smaller blast radius than the previous run. The browser-overlay detector from the previous critique (which had flagged low-contrast, undersized-ui-text, pulsing-dot, dark-glow, gpt-thin-border-wide-shadow on login, gradient text, eyebrows, cream palette) was *not* re-run because no Playwright/Puppeteer tool was available in the sub-agent — the Assessment B agent fell back to CLI + static DOM only, and WebFetch refused `localhost`. So contrast, type-size, and theme-asymmetry regressions that the previous run surfaced cannot be re-verified here. CLI on this dirty subset returned zero hits for `low-contrast`, `undersized-ui-text`, `pulsing-dot`, `dark-glow`, `gpt-thin-border-wide-shadow`, `gradient-text`, `ai-color-palette`, `bounce-easing`, `flat-type-hierarchy`, `tiny-text`. Manual inspection of `tokens.css` via curl confirms the token system is intentionally restrained: oklch with alpha-bounded glows, no purple gradients, Inter + JetBrains Mono pairing rather than monoculture. This is a genuine *improvement signal*: the worst AI-slop patterns from the prior run appear to have been edited out, and the token layer is defending against them.

**Visual overlays**: FALLBACK — no browser mutation tool was available in the Assessment B sub-agent, so no user-visible overlay was injected. Findings above are CLI scan + LLM source review only.

**Where A and B disagree productively**: the LLM review flags *information hierarchy and decision architecture* problems (threshold as ordinary card content, decision overload, silent errors) that the detector cannot see. The detector flags *structural repetition* (`side-tab` × 3 across three views — a missing primitive, not three isolated bugs) and *layout-thrash patterns* (`width` transitions on sidebar collapse) that the LLM could note but not enforce as a class. They agree on the side-tab strip in `EngineView.vue:255` being ornamental-with-weak-justification (LLM: amber is for last-sig which is semantically tinted; detector: 3px is heavy and reads as AI tell). Where the detector catches something A missed: the layout-transition cluster in `AppSidebar.vue` is the single biggest jank risk on every route change, and the side-tab pattern is *systemic* (three views, three implementations of the same strip) rather than one-off.

## Overall Impression

A disciplined, coherent system with genuine craft at the token layer — that's the honest headline. The token discipline, the mono numerics, the scan-loop control as a true hero, and the recent safety improvements (`ConfirmModal` for delete/stop/discard, the deleted unused `useCountdown`) are real progress. The system is undermined by three facts that haven't been resolved since the last critique: (1) the product's central contract — *threshold truth* — is treated as ordinary card content rather than the dominant visual comparison on every signal row; (2) silent failure in Engine polling makes "quiet" indistinguishable from "disconnected" on a monitoring product; (3) History and Settings expose decision surfaces wide enough that finding one signal competes with administering the system. The detector's quieter finding — the 3px side-tab is implemented three different ways across three views because there's no shared primitive — is the single highest-leverage cleanup: define the strip once, replace three implementations.

## What's Working

1. **Token-system discipline has actually improved.** 132 OKLCH variables, coherent dark/light theming, alpha-bounded glows, restrained shadows, Inter + JetBrains Mono pairing rather than monoculture — the previous run's neon-gradient / dark-glow / pulsing-dot warnings don't reappear in the dirty subset. Rare coherence for a solo-built dashboard.
2. **Operational state is given visual form.** The scan countdown + progress track + chart/analysis counts + pause/resume actions + polling copy make a live system legible (`DashboardView.vue:141-176`; `AppSidebar.vue:97-116`). The scan-bar is a true hero element, correctly duplicated in the sidebar foot so control is one click away on any page.
3. **Recent safety work is meaningful.** Delete / stop-engine / discard flows now use `ConfirmModal.vue` with disabled/loading states (`ConfirmModal.vue:20-30`; `NotificationsView.vue:133-141`; `StrategyView.vue:105-113`). The `useCountdown` orphan was deleted — dead-code cleanup is happening.

## Priority Issues

### [P0] Threshold truth is buried in ordinary card content
- **What**: The dashboard surfaces `threshold` and computes qualifying signals server-side, but threshold context is one data field among many (`DashboardView.vue:28`, `178-180`, and the signals section beneath; backend `app/routes/dashboard.py:69-71` filters separately).
- **Why it matters**: The product's central contract is "fire Telegram notifications above a threshold." If score, threshold, direction eligibility, and delivery status aren't immediately comparable, operators can't audit or trust the monitor during a live event — they have to do the comparison in their head. Same problem on History rows and Notifications rows.
- **Fix**: One "signal qualification" block per signal row: `8.7 score / 8.0 threshold · LONG eligible · Telegram delivered`. Reuse across Dashboard, History, AnalysisDetail, Notifications. The ScoreBar's green/amber/red bands at 7/5 are also disconnected from the real threshold — bands should derive from configured threshold, not be hard-coded.
- **Suggested command**: `/impeccable clarify`

### [P0] Silent polling failures make "quiet" indistinguishable from "disconnected"
- **What**: `EngineView.vue:54-57, 83-105` and `AppSidebar.vue:31-36` `.catch(() => {})` every poll. Logs section loads silently on failure. The sidebar status pill shows a state but never indicates staleness.
- **Why it matters**: A monitoring product must distinguish "no activity" from "the monitor is disconnected." On this product, a backend outage produces an empty dashboard that reads as healthy.
- **Fix**: Per-surface connectivity state, last-successful-update timestamp, "data may be stale (last update 4m ago)" banner, visible Retry button. Keep the last-known state but make its age explicit. Apply to EngineView, sidebar status, log panel, dashboard charts.
- **Suggested command**: `/impeccable harden`

### [P1] History and Settings expose too many decisions at once
- **What**: History combines filtering, sorting, page size, pagination, resend, reanalyze, delete, and row navigation in one workflow (`HistoryView.vue:28-39`, `87-133`). Settings presents six sections and many fields with repeated card headers and save controls (`SettingsView.vue:26-33`, `117-607`).
- **Why it matters**: Operators need fast scanning and safe decisions, not a control-panel maze. Excess controls increase misconfiguration and make the primary task — *find and inspect a signal* — compete with system administration. 4 cognitive-load checklist failures (single focus, chunking, one-thing-at-a-time, minimal choices).
- **Fix**: Make "Find a signal" the default History task — compact filter row, expandable Advanced filters. Group Settings into three domains (Monitor / Signal & Delivery / Integrations) with one sticky Save per group. Collapse advanced sections by default.
- **Suggested command**: `/impeccable distill`

### [P1] Destructive / externally consequential actions lack consequence communication
- **What**: Delete actions are confirmed but irreversible; resend (creates duplicate Telegram), reanalyze (alters interpretation), run-now, and engine stop don't explain consequences or provide post-action recovery (`NotificationsView.vue:46-57`, `HistoryView.vue:108-133`, `EngineView.vue:59-80`, `DashboardView.vue:57-76`).
- **Why it matters**: A notification resend can create duplicate Telegram messages; reanalysis changes interpretation; stopping the engine changes monitoring coverage. Confirmation alone is not sufficient risk communication.
- **Fix**: Consequence-specific confirmation copy with target identity and idempotency state. For resend, show "last sent at" and prevent duplicate within a short window unless explicitly overridden. Consider Undo/Restore for local records.
- **Suggested command**: `/impeccable harden`

### [P2] The 3px side-tab strip is implemented three times instead of once
- **What**: `DashboardView.vue:282` (`.scan-bar`), `EngineView.vue:255` (`.last-sig`), `StrategyView.vue:129` (`.info-bar`) all re-implement `border-left: 3px solid var(--<color>)` on cards with non-zero border-radius. The detector flagged all three.
- **Why it matters**: System-level pattern, not one-off. A redesign of the strip pattern requires touching three views instead of one. Each variant drifts slightly in color and radius. Heavy 3px reads as an AI-tell on a dark UI.
- **Fix**: Extract one `<SideAccentCard>` (or `.accent-bar-card` utility) with size + color + radius props. Replace the three implementations. Use a thinner 2px or a left-edge glow rather than a 3px solid strip.
- **Suggested command**: `/impeccable distill`

### [P2] Layout-transition on sidebar collapse causes route-change jank
- **What**: `AppSidebar.vue:140` and `:324` animate `width` (220→56 desktop, 0→220 mobile). `DashboardView.vue:312` animates the progress-fill width.
- **Why it matters**: Width transitions force flexbox re-layout on every frame for 350ms — the single biggest jank risk on every route change. Mobile drawer has a transform leg that *is* GPU-accelerated; the width leg is the offender.
- **Fix**: Use `transform: scaleX(...)` mirror or `grid-template-columns` trick for the desktop collapse. Keep the transform leg for mobile, drop the width leg. Progress-fill width is borderline acceptable (single-child fill, 500ms ease-out, negligible layout impact) — keep but consider a `transform-origin: left; transform: scaleX(...)` alternative.
- **Suggested command**: `/impeccable optimize`

## Persona Red Flags

**Alex (Power User)**: History has no expert accelerators — no keyboard shortcuts, no command palette, no saved filters, no bulk operations (`HistoryView.vue:28-39`, `87-133`). Engine logs poll every 2s with auto-scroll (`EngineView.vue:83-90`, `108-110`) but no pause/freeze, no search, no level filter, no copy. Seven sidebar destinations visible with no "recent analyses" or contextual cross-links (`AppSidebar.vue:16-24`). Export CSV is presumably still disabled (carryover from prior critique).

**Sam (Accessibility)**: Color carries too much semantic weight — LONG/SHORT, success/error, running/paused rely heavily on green/red/amber (`BaseChip.vue:47-49`, `StatusPill.vue:33-35`, `PulseIndicator.vue:35-41`). Password visibility control is removed from keyboard order via `tabindex="-1"` (`LoginView.vue:76-84`). Mono labels and metadata are often 11–12px (`global.css:212-218`, `StatCard.vue:48-52`, `AppTopbar.vue:88-101`) — readability pressure for low-vision users. Toasts use `role="status"` even for errors (`AppToast.vue:19-22`), weakening urgent feedback semantics. Score level may be color-only (prior critique noted double-encoding for direction but not for score).

**Riley (Stress Tester)**: Backend outage looks identical to a quiet monitor (`EngineView.vue:54-57`, `83-105`; `AppSidebar.vue:31-36`). Double-submit protection is inconsistent — `ChartsView.vue:90-105` deletion has no visible action-loading binding in `confirmDelete`. Live motion (pulsing dots, page transitions) is globally enabled (`tokens.css:126-133`; `PulseIndicator.vue:35-46`; `global.css:18-32`) without unified signal-urgency or stale/live distinctions. Theme asymmetry: `--green-2`, `--amber-2`, but `--blue` is defined in dark only — light-theme use of `var(--blue)` would inherit dark values silently (carryover risk).

## Minor Observations

1. `tokens.css:5-17` has a strong dark surface ladder, but `--muted` and `--muted-2` are nearly identical — secondary-text hierarchy is weak.
2. `tokens.css:89-90` puts glass blur in core vocabulary though most cards are solid — reserve blur for transient chrome.
3. `global.css:14` sets `body { overflow: hidden }`; every route depends on nested scroll containers — complicates zoom and assistive tech.
4. `AppSidebar.vue:204-213` places the active rail at `left: -8px` — can clip or detach from the active item.
5. `AppTopbar.vue:12-15` falls back every missing breadcrumb to "Dashboard" — misrepresents location.
6. `AppToast.vue:49` caps width at 360px but no mobile positioning adjustment — long errors crowd narrow screens.
7. `StatCard.vue:20-23` renders either delta or hint, never both — useful trend context disappears when a hint is supplied.
8. `StatusPill.vue:2-10` maps `sent` and `ok` to the same green — conflates delivery success with generic operation success.
9. `LoginView.vue:100-102` exposes implementation/vendor details ("TradingView · NVIDIA MiniMax-M3 · Telegram delivery") before authentication.
10. `SettingsView.vue:154-163` provides a 17-option timezone select without search or type-ahead.
11. Live server was started on port 8400, PID 77270, then killed cleanly — no orphan process left behind.

## Questions to Consider

1. What should an operator know in the first three seconds of a signal event — that the engine is alive, that the score crossed threshold, or that Telegram delivered? Can one visual unit communicate all three?
2. If the threshold is the product's central contract, why is it not the dominant comparison on every signal row?
3. Should "quiet" be presented as a healthy monitored state with coverage evidence (last scan, last delivery, age), rather than an empty list?
4. What would happen if History opened in a saved "actionable signals" view instead of exposing every analytical control immediately?
5. The 3px side-tab strip is implemented three different ways — defining it once and replacing three implementations would compound into the next several cleanup passes. Worth its own small refactor before any visual-world decision is made?
